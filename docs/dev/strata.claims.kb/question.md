# The questions -- driving problems the tower was bought to settle

The core design problems the ledger resolves: historically first --
everything downstream is their decomposition; logically last --
stating what decomposes a question takes the whole tower's vocabulary.
Three were ill-posed as experienced (IDENTITY, SEMANTICS,
FRAGMENTATION); their settlement was mostly re-posing.

| The question | Decomposed by | Open residue |
|---|---|---|
| IDENTITY -- of what object is a kb a presentation? | WORD, FOLD, STRATA, TWICE | the missing law: MERGE |
| STORAGE -- what may be stored, what must be computed? | COMPUTED, ASYMMETRY, OVERSHOOT | -- |
| EXTENSION -- when is a genre safe to add? | SATISFACTION, FREE_CONSERVE | the proof: OBLIGATION |
| SEMANTICS -- must the store choose a defeat semantics? | DEFEAT, APPROX, STANCE | dissolved: stance-indexed choice |
| STALENESS -- what does a derived document promise? | TRIANGLE, DEBT, DERIVATIVE, FRESH_COST | the constants are empirical |
| RETENTION -- how does a property survive a redesign? | GRADE, FLOOR, MONITOR | the kernel rung: OBLIGATION |
| PORTING -- what survives a port? | PRIOR_ART, MIGRATE | -- |
| FRAGMENTATION -- why did the fleet fragment? | FLEET_MAP, STRATA | v2's shape -> `design-next.kb/` |

The view function, so that this is a view and not a second ledger:
each row is one file of `question.kb/`; *decomposed by* is the labels
on its `why:`, in order, less any that stands `open`; *open residue*
carries those, plus prose where the residue is not a claim. Argue
with the files, not with the table.
